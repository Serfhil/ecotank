# EcoTank — правила проекта

Этот файл — единственный свод правил проекта. Он обязателен для каждого, кто меняет репозиторий: людей и любых ИИ-агентов (Claude, Codex и других). `CLAUDE.md` подключает этот файл целиком и своих правил не содержит.

Правила ниже непреложны. Слова «запрещено», «только», «обязан» значат ровно это: исключений по усмотрению исполнителя нет. Единственный законный путь отступить от правила — раздел 0.

Что где лежит и как запускать — в [README.md](README.md). Задачи для агентов — в [prompts/](prompts/README.md).

## 0. Статус правил

1. **Правила нельзя нарушать молча.** Если задача не решается без нарушения правила, работа останавливается до решения пользователя. Пользователю сообщают: какое правило мешает, почему без этого не обойтись, какие есть варианты и чем каждый обернётся.
2. **Правило меняется раньше кода.** Если пользователь согласился, сначала правится этот файл (и `checks/rules.cjs`, если правило проверяется автоматически), затем код. Правка правил — отдельный пункт в отчёте о работе.
3. **Проверку нельзя ослаблять, чтобы она прошла.** Упавшая проверка означает одно из двух: сломано поведение (чинится код) или намеренно изменено поведение (проверка переписывается под новое поведение, и об этом сказано в отчёте). Удалять проверку, расширять допуски и добавлять исключения в списки `checks/rules.cjs` можно только по пункту 1.
4. **Расширение — нормальная работа, а не нарушение.** Новое поле в `KINDS`, новая функция сценария в `scenarios.js`, новый предикат в `world.js` разрешены, если сделаны по разделу 10. Нарушение — это обход: условие по имени в ядре, второе место для того же числа, состояние без владельца.
5. **Правила важнее задачи.** Если текст задачи (в том числе промпт из `prompts/`) противоречит правилам, действует пункт 1: исполнитель не выбирает сам, чему следовать.
6. **Незнание не оправдание.** Перед первой правкой в сессии исполнитель читает этот файл целиком, а перед правкой файла — его шапку.
7. Пометка **[П1]…[П11]** означает, что правило проверяет `checks/rules.cjs`; остальное проверяет `checks/modules.cjs` или ревью.

## 1. Неизменные свойства продукта

1. Игра открывается двойным щелчком по `index.html` с диска. Запрещены сборка, пакеты, модули ES, `fetch` своих файлов и всё, что требует сервера. **[П2]**
2. Зависимостей во время работы нет. Инструменты разработки (Node для проверок, Prettier для форматирования, Python для подготовки спрайтов) игре не нужны.
3. Подключение любого файла из `js/` только объявляет данные и функции. Оно не трогает DOM, не читает сохранения, не создаёт объекты игры и не вешает обработчики. Всё запускает `bootGame()`; модуль с инициализацией даёт функцию `init…()`, которую можно вызвать повторно без дублей.
4. В `index.html` нет кода игры: только разметка, стили, список `<script>` и вызов `bootGame()`. Порядок скриптов задан в одном месте — `index.html`, и закреплён в `checks/modules.cjs`. **[П2]**
5. Каждый файл `js/` начинается с `'use strict';` и комментария: за что файл отвечает, чем владеет, от чего зависит. **[П1]**

## 2. Источники правды

У каждого факта одно место. Второе место для того же факта — нарушение, даже если значения сейчас совпадают.

| Что | Где | Правило |
|---|---|---|
| Вид техники: числа, название, сторона, поведение, снаряд, гибель, спрайт | `KINDS` в `js/config.js` | Логика читает поля `KINDS[kind]`. Сравнивать `kind` с именем врага запрещено. **[П4]** |
| Ступень танка игрока: здоровье, размер, орудие, пулемёт, взрывы, иллюстрация | `PLAYER_TIERS` в `js/config.js` | Только `playerTier(t)`, `usesTier(t)`, `MAX_TIER`. Сравнивать `upgrade` с числом запрещено. **[П5]** |
| Баланс | `CFG` в `js/config.js` | Каждый ключ `CFG` имеет строку в `CFG_FIELDS`, и наоборот. Ключа, который никто не читает, быть не должно. |
| Выбор игрока (размер поля, режим, карта, уровень) | `PREFS` в `js/config.js` | В `CFG` выбор игрока не кладут. |
| Бонус: вид, полезность, действие | `ITEMS` в `js/pickups.js` | Условий по типу бонуса вне записи `ITEMS` нет. |
| Состав волн обычного боя | `WAVE_MIX`, `WAVE_EXTRAS` в `js/waves.js` | |
| Поведение врага | `ENEMY_AI` в `js/enemy-ai.js` | Ключ — `KINDS[kind].ai`. |
| Символ карты: тип клетки, покрытие, кисть, цвет | `CELL_CATALOG` в `js/world.js` | Регулярок и списков символов в других файлах нет. |
| Проходимость и простреливаемость | предикаты `blocks…` в `js/world.js` | Собственные списки типов клеток в логике запрещены. |
| Зона и контур базы | `baseZone`, `baseWallCells` в `js/world.js` | |
| Сценарий | один файл `js/scenario-<имя>.js` (или группа файлов с общим префиксом) | См. раздел 4. |
| Тексты интерфейса | `UI_TEXT` в `js/ui-text.js` | Строк для игрока в логике нет. Неиспользуемых ключей нет. **[П8]** |
| Сюжетные тексты сценария | файлы этого сценария | |
| Значения по умолчанию | только `js/config.js` | Копий «на всякий случай» (JSON, таблицы в логике, числа в проверках) не держат. |
| Порядок подключения | `index.html` | README его не повторяет. |

Число, которое задаёт поведение и встречается больше одного раза, получает имя (константу рядом с кодом или поле в `config.js`). Число, которое пользователь может захотеть настроить, идёт в `CFG` или `KINDS`.

## 3. Владение состоянием

1. Игра — классические скрипты с общей глобальной областью. Поэтому у каждой глобальной переменной и функции ровно одно объявление и один файл-владелец, названный в шапке файла. **[П9]**
2. Состояние боя (`state`, `player`, `enemies`, `allies`, `bullets`, `items`, `wrecks`, …) объявлено в `js/game.js`. Поле (`grid`, маски, покрытия, `geoVersion`, `simTime`) — в `js/world.js`. Состояние подсистемы (`rockets`, `bombers`, `tacGroups`, …) — в файле подсистемы.
3. Читать чужое состояние можно. Заменять чужой массив или сбрасывать чужой таймер — только функцией владельца (`clearBattlefield()`, `resetSappers()`, `dropUnavailableItems()`, `setBaseWall()`). Если нужной функции нет, её добавляют владельцу.
4. Новый массив боевых объектов сбрасывается в `clearBattlefield()` (живёт в пределах волны) или `resetOperation()` (в пределах операции). Сброс по месту — в `startGame`, `toMenu`, в сценарии — запрещён.
5. Новые поля, которые подсистема хранит на танке, лежат в одном объекте подсистемы (`e.tac`, `e.salvo`), а не россыпью на верхнем уровне. Поля, общие для всех машин, создаёт `makeTank()`.
6. Хранилище браузера читают и пишут только владельцы сохранений: `settings.js` (настройки), `world.js` (карты, пресеты, прогресс кампании), `game.js` (рекорд), `preset-editor.js` (состояние редактора). Каждый вызов — в `try/catch`; загруженные данные проверяются перед применением. **[П7]**
7. В настройках браузера хранятся только отличия от `config.js`. Сохранять `KINDS` или `CFG` целиком запрещено: иначе правки баланса не дойдут до игроков. Смена формата сохранения — новый ключ и перенос старых данных.

## 4. Ядро и сценарии

1. Ядро (`game.js`, мир, танки, оружие, урон, ИИ, отрисовка, меню) не знает сценариев по имени. Условия вида `if (raseiniai)`, сравнения `scenario.id` с именем и вызовы функций сценария из ядра запрещены. **[П3]**
2. Ядро обращается к сценарию только через необязательные функции активного сценария, перечисленные в шапке `js/scenarios.js`. Этот список — контракт.
3. Сценарию нужно то, чего нет в контракте: в `scenarios.js` добавляется новая функция с описанием, ядро вызывает её для всех сценариев одинаково. Сценарий не правит ядро под себя.
4. Состояние сценария принадлежит файлам сценария, создаётся в `start()` и убирается в `stop()`.
5. Возможность, нужная одному сценарию, но относящаяся к миру или технике (фигурное препятствие, сценарный выезд, колонна), делается общей возможностью ядра без упоминания сценария — как `addSolid()` и `driveExit()`.
6. Режим, отличающийся только расстановкой поля, — это значение `PREFS.mapMode`, а не новый сценарий.

## 5. Время, случайность, кадр

1. Логика знает время только через `dt`. `setTimeout`, `setInterval`, `Date`, `performance.now` в логике запрещены; игровые события считаются счётчиком, который уменьшается на `dt`. Единственное исключение — игровой цикл в `bootGame()`. **[П6]**
2. Случайность — только `Math.random` (и `rnd`/`ri` поверх него). Проверки подменяют его генератором с зерном. **[П6]**
3. Результат не зависит от частоты кадров. Всё, что копится по кадрам, обязано давать тот же итог при 30, 60 и 144 кадрах в секунду и иметь проверку на это (пример — артподготовка в `checks/support.cjs`).
4. Новые часы не заводят: время симуляции — `simTime`, время интерфейса — `time`. Существующие `supportClock`, `rocketClock`, `tacClock` — долг; новый код на них не опирается.
5. Игровая логика не зависит от DOM, загрузки картинок и размеров окна. Размеры и хитбоксы — из `config.js`, а не из спрайта. Если картинка не загрузилась, игра продолжает работать.
6. Тяжёлые расчёты не выполняются каждый кадр на каждую машину. Поле маршрута берут из `routeField()`: оно кэшируется и пересчитывается после изменения `geoVersion`. Общего поля маршрута нет и быть не должно.
7. Любое изменение проходимости клетки увеличивает `geoVersion`.

## 6. Стиль кода

1. Код форматирует Prettier с настройками из `.prettierrc.json`. Перед сдачей работы: `npx prettier --write js check.cjs checks scripts`. Плотные строки «всё в одну» запрещены. **[П10]**
2. Комментарий объясняет, зачем код такой и какое правило игры он воплощает. История правок («раньше было», «как прежде», «больше не») в комментариях запрещена: для неё есть `CHANGELOG.md` и git.
3. Комментарии и документы — по-русски. Имена в коде — по-английски, по смыслу. Новые ключи `UI_TEXT` — camelCase по смыслу (`hudEnemiesShort`), а не транслит фразы и не `имя_2`.
4. Мёртвого кода нет: неиспользуемые функции, поля, ключи настроек, тексты и ассеты удаляются в той же правке, которая сделала их ненужными.
5. Проверки `typeof X !== 'undefined'` для своих же глобальных имён не пишут: порядок подключения гарантирует их наличие.
6. Процедурные модели техники в `render-tanks.js` — запасной вид на случай незагруженного спрайта. Только в файлах отрисовки допустимы условия по виду ради внешности.

## 7. Проверки

1. Перед сдачей любой правки проходят `node check.cjs` и `node checks/integration.cjs`. Если что-то не запускалось или упало, об этом сказано в отчёте.
2. Правка интерфейса, запуска или порядка скриптов дополнительно проверяется в браузере: страница открывается с `file://` без ошибок в консоли.
3. Новое поведение приходит со своей проверкой в `checks/`. Исправление ошибки приходит с проверкой, которая без исправления падает.
4. Проверка закрепляет поведение, видимое игроку, а не внутренности: не точные значения из `config.js`, а связь («перезарядка врага равна `KINDS[kind].fireRate`»).
5. Проверки, зависящие от случайности, работают с зерном.
6. Проверки не требуют установки пакетов.

## 8. Документы

1. `README.md` описывает проект, каким он является сейчас: что это, как запустить, структура, управление. Истории в нём нет.
2. `CHANGELOG.md` — одна запись на заметное игроку или разработчику изменение.
3. `AGENTS.md` — правила; `CLAUDE.md` только подключает его. Копировать правила в другие файлы запрещено.
4. `prompts/` — задачи для агентов (раздел 9). Других мест для задач нет: файлы задач в корне и в `docs/` не создают.
5. Отчёты о задачах, заметки о ходе работы, снимки проверок и копии настроек отдельными файлами в репозиторий не кладут. Итог задачи записывается в её файл в `prompts/`. Вывод, который нужен надолго, превращается в правило здесь или в комментарий у кода.
6. Правка, которая меняет структуру, управление или рецепты из раздела 10, обновляет документ в той же правке.

## 9. Задачи для агентов (`prompts/`)

1. Задача для агента — файл `prompts/ГГГГ-ММ-ДД-краткое-имя.md`. Когда пользователь ссылается на задачу, промпт или ТЗ, искать его нужно в `prompts/`.
2. В начале файла, сразу после заголовка, стоит строка статуса: `**Статус:** новая`, `в работе`, `выполнено` или `отложено` — и после неё дата. **[П11]**
3. Задачу берут в работу только по прямому указанию пользователя. Наличие файла со статусом «новая» — не разрешение его выполнять.
4. Взяв задачу, агент ставит статус «в работе». Закончив — «выполнено» с датой и дописывает в конец файла раздел `## Итог`: что сделано, что не сделано и почему, какие проверки запускались и с каким результатом, какие правила пришлось менять по разделу 0.
5. Текст задачи выше раздела «Итог» агент не переписывает: это запись того, что просил пользователь. Уточнения пользователя дописываются в раздел `## Уточнения` с датой.
6. Если задача выполнена частично или остановлена по разделу 0, статус — «отложено», а в «Итоге» указано, чего не хватает для продолжения.
7. Выполненные задачи не удаляют и не перемещают: статус в файле — единственный признак состояния. Списка задач с дублированием статусов не ведут.
8. Подробный порядок и шаблон — в [prompts/README.md](prompts/README.md).

## 10. Рецепты

Если по рецепту требуется править файл, которого в нём нет, — это сигнал: либо рецепт устарел (обновить), либо правка идёт в обход правил.

**Новый вражеский танк.**
1. Запись в `KINDS` (`config.js`): `name` (ключ в `UI_TEXT`), `side: 'enemy'`, `ai`, числа, `score`, `scrap`, цвета; при необходимости `column`, `shot`, `deathBlasts`, `burns`, `breaksWalls`, `light`.
2. Спрайт: `sprite: '<имя>'` и файлы `assets/vehicles/<имя>-hull.png`, `-tracks.png`, `-gun.png`, `-turret.png` (или `sheet`). Без спрайта рисуется общая процедурная модель.
3. Появление: строка в `WAVE_MIX` или `WAVE_EXTRAS` (`waves.js`) либо появление в сценарии.
4. Если пулемёт должен его брать — число попаданий в `PLAYER_TIERS[n].mg.hits`.
5. Панель разработчика, статистика, титры победы и колонны подхватят вид сами. Новое поведение — новая запись в `ENEMY_AI` и функция обновления в своём файле.

**Новое свойство техники.** Поле в `KINDS` с описанием в шапке таблицы и чтение этого поля в логике. Не `kind === '…'`.

**Новый бонус.** Запись в `ITEMS` (`pickups.js`): `color`, `glyph`, `name` и либо `timed: true`, либо `useful(t)` и `apply(t, it)`. Эффект временного бонуса читается из `t.pw.<тип>`.

**Новая ступень танка.** Запись в конец `PLAYER_TIERS`, спрайты `assets/vehicles/<sprite>-*.png`, иллюстрация поражения.

**Новый сценарий.**
1. Файл `js/scenario-<имя>.js` с одним `defineScenario('<имя>', { start, … })`; `start()` первым делом вызывает `activateScenario('<имя>')`, затем `resetOperation()`.
2. Строка `<script>` в `index.html` после `game.js` и то же имя в списке `checks/modules.cjs`.
3. Кнопка в меню: элемент в `index.html` и `menuButton: '<id>'` в сценарии.
4. Проверка в `checks/`, которая проходит сценарий от старта до исхода.
Образцы: `scenario-waves.js` (простой), `raseiniai*.js` (сюжетный).

**Новая клетка карты.** Запись в `CELL_CATALOG` (`world.js`), CSS-класс `.t-<символ>` в `index.html`, рисунок миниатюры в `map-editor.js`. Новый **тип** клетки дополнительно учитывается в каждом предикате `blocks…`, в столкновениях (`tileRects`) и в отрисовке.

**Новая настройка.** Ключ в `CFG` и строка в `CFG_FIELDS`; для техники — поле в `KINDS` и, если оно новое, строка в `TANK_FIELDS`.

**Новая готовая карта.** Строки в `maps.js`; затем `node scripts/prepare-ai-markup.cjs` для тактической разметки.

## 11. Git

- Когда пользователь говорит «стянуть с репозитория» (pull from the repository), приоритет у репозитория: при конфликтах и расхождениях остаётся версия из репозитория, а не локальные правки.
- По умолчанию отправка идёт в `main`. Отдельную ветку создают только по явной просьбе пользователя.
- Перед коммитом выполнен раздел 7, а у задачи из `prompts/` обновлён статус.
