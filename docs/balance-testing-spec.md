# ТЗ: автоматические тесты баланса EcoTank

Документ для того, кто будет писать и сопровождать тесты баланса. Описывает, какие уровни тестов нужны, в каком порядке их делать, как формулировать цели и что учитывать, чтобы тесты оставались полезными при дальнейших правках игры.

Без отдельной санкции не делать эту задачу.
 

---

## 1. Цель

Получить набор скриптов, которые:

1. **Сразу показывают, как правка чисел** в `js/config.js` (и других параметров) **изменила баланс**: кто стал опаснее, какая волна или уровень стали сложнее.
2. **Ловят выход баланса за рамки замысла**, например «волна 5 легче волны 4» или «первый уровень почти непроходим».
3. **Находят перекосы, до которых сложно додуматься вручную**: доминирующие стратегии, бесполезные бонусы, эксплойты AI, скачки сложности в кампании.

Тесты проверяют **соответствие замыслу**, а не «хороший ли баланс». Замысел (коридоры значений) утверждает автор игры.

---

## 2. Как игра запускается в тестах

Основа уже есть в проекте: `check.cjs`, `checks/integration.cjs`.

- Тест читает `index.html` и выполняет все `<script>` по порядку внутри песочницы `node:vm`.
- Браузерные API (`document`, canvas, `localStorage`, `Audio`, `Image`) заменены пустышками. Отрисовка ничего не делает.
- `Math.random` подменяется генератором с фиксированным зерном:
  ```js
  math.random = () => { seed = (Math.imul(seed, 1664525) + 1013904223) >>> 0; return seed / 4294967296; };
  ```
  Одно зерно — один и тот же бой при каждом запуске. Падение всегда воспроизводимо.
- Время прокручивается вызовом `update(1/30)` в цикле. Это та же функция, что работает в браузере.
- Внешние пакеты не нужны, только Node.js.

**Измеренная скорость** (Windows 10, Node 26, 12 ядер):

| Показатель | Значение |
|---|---|
| Кадров в секунду на одном ядре, без отрисовки | ~2900 (в ~96 раз быстрее реального времени) |
| На 12 ядрах (`worker_threads`) | в ~1000 раз быстрее реального времени |
| Минута игры | ~0.6 с на ядре |
| Кампания (15 уровней, ~45–60 мин игры) | ~30 с на ядре |

## 3. Общие правила для всех уровней

### 3.1. Коридоры, а не точные числа
- Проверка формулируется как диапазон или сравнение: «медиана 10–18 с», «heavy опаснее scout».
- Точные значения («ровно 13.1 с») запрещены: они ломаются от любой безобидной правки.
- Сравнения предпочтительнее абсолютных чисел, они переживают перенастройку.
- Стартовые коридоры, пока автор не задал свои: текущее значение ±25%.

### 3.2. Много зёрен
- Один запуск ничего не доказывает. Каждый сценарий гоняется на 20–100 зёрнах.
- В проверке используются медиана, доля побед, 10-й и 90-й перцентили.
- Набор зёрен фиксирован в коде теста (например, 1001–1020), чтобы результат был стабильным.

### 3.3. Два режима каждого скрипта
| Команда | Поведение |
|---|---|
| `node check-balance.cjs` | Проверяет коридоры. Выход с кодом 1 и понятным сообщением при нарушении |
| `node check-balance.cjs --report` | Печатает таблицы метрик и разницу с `balance-baseline.json` в процентах |
| `node check-balance.cjs --report --save` | Перезаписывает `balance-baseline.json` текущими метриками |

Сообщение об ошибке должно объяснять суть: `heavy убивает стоящего игрока за 6.2 с (медиана 20 зёрен), ожидали 10–18`.

### 3.4. Изоляция сценария
- В дуэлях и точечных сценариях отключать всё постороннее: `CFG.bomberChance = 0`, `CFG.rocketChance = 0`, пустое поле (`grid.fill(EMPTY)`), пустая очередь `toSpawn`, неуязвимая база (`base.hp = 99999`), `muted = true`.
- Каждый прогон запускается на свежей песочнице или после полного `startGame()`, без утечки состояния между зёрнами.

## 4. Уровни тестов: что за чем делать

Уровни идут по возрастанию стоимости и сложности. Каждый следующий опирается на предыдущий. **Делать по порядку.**

### Уровень 0. Инфраструктура

**Сделать:**
1. Вынести загрузку игры в песочницу в общий модуль `scripts/balance/boot.cjs`: `boot(seed) → run(code)`. Сейчас этот код продублирован в нескольких `check-*.cjs`.
2. Сделать слой `scripts/balance/sim.cjs`, единственную точку контакта тестов с игрой:
   - `reset({ seed, mode, level, mapSize })` — старт игры;
   - `spawn(kind, x, y)`, `clear()` — подготовка сценария;
   - `step(n)` — прокрутить n кадров по 1/30 с;
   - `observe()` — состояние в виде простого объекта (игрок, враги, снаряды, база, волна, уровень, `state`);
   - `act({ move, turn, aimX, aimY, fire, special })` — управление танком игрока через `keys`/`mouse`.
3. Утилиты статистики: медиана, перцентили, доля, форматирование таблиц.

**Готово, когда:** слой `sim` проходит самопроверку (детерминизм: два прогона с одним зерном дают идентичный `observe()` через 1800 кадров).

**Зачем:** при переименованиях внутри игры чинится только `sim.cjs`, все тесты выше остаются нетронутыми.

### Уровень 1. Аналитические проверки (мгновенные)

Числа берутся прямо из `KINDS`, `CFG`, `waveList()`, `maxAlive()`, без симуляции боя.

**Метрики:**
- Состав волн 1–15: среднее число врагов каждого типа (по 200 выборкам `waveList(w)`), суммарное HP, суммарный теоретический урон в секунду (`dmg / fireRate`), лимит одновременных врагов.
- Теоретическая смертоносность каждого типа: время до гибели игрока при 100% попаданий = `ceil(player.hp / dmg) × fireRate`.
- Ценность врага: очки и металлолом относительно его HP и смертоносности.

**Примеры проверок:**
- Суммарное HP каждой волны больше предыдущей на 10–40%.
- Доля heavy не превышает 35% (сейчас это зашито в `waveList`).
- Очки за врага растут вместе с его опасностью: порядок по `score` совпадает с порядком по HP × урон/с с допуском.

**Время прогона:** < 1 с. **Входит в `node check.cjs`.**

### Уровень 2. Дуэли (секунды)

Игрок против одного врага на пустом поле, 20+ зёрен на сценарий.

**Сценарии:**
1. **Пассивная живучесть:** игрок стоит и не стреляет, враг в 300 px. Метрика: время до гибели игрока.
2. **Активная дуэль:** игрок управляется простым ботом (целится в ближайшего врага, стреляет при готовности, не двигается). Метрики: доля побед, время победы, потерянное HP.
3. **Влияние улучшений:** сценарий 2 при `setPlayerUpgrade(player, 0 | 1 | 2)`.
4. **Влияние бонусов:** сценарий 2 с активным `rapid`, `shield`, `rail`.
5. **Враг против союзника:** `ally` против каждого типа.

Типы врагов: `scout`, `soldier`, `heavy`, `artillery`, `rocket`, `moto` (у moto своя метрика: время до установки мины), смертник (бомбер).

**Примеры проверок:**
- heavy убивает стоящего игрока быстрее scout.
- Игрок без улучшений побеждает soldier в 70–95% дуэлей.
- С улучшением 2 игрок побеждает soldier хотя бы в 1.5 раза быстрее, чем без улучшений.

**Стартовые данные (проба от 08.11.2026), сценарий 1, медиана 20 зёрен:**

| Враг | Секунд до гибели стоящего игрока |
|---|---|
| soldier | 9.3 |
| artillery | 10.5 |
| scout | 12.4 |
| heavy | 13.1 |

> Требует решения автора: heavy (урон 2) убивает почти так же медленно, как scout, из-за перезарядки 5 с. Задумано ли это?

**Время прогона:** 5–20 с. **Быструю часть можно включить в `node check.cjs`.**

### Уровень 3. Скриптовый бот: прохождение волн и уровней (минуты)

Бот с понятными правилами и набором параметров:

| Параметр | Смысл |
|---|---|
| `keepDistance` | Желаемая дистанция до врага, px |
| `dodgeThreat` | На каком расстоянии до летящего снаряда начинать уклонение |
| `pickupRadius` | Ехать за бонусом, если он ближе этого расстояния |
| `targetPriority` | Порядок выбора цели: ближайший / самый опасный / самый слабый |
| `baseGuard` | Насколько держаться у базы (0 — игнорировать, 1 — не отъезжать) |
| `useSpecial` | Когда применять спецспособности и артподготовку |

**Обязательные «человеческие» ограничения:**
- задержка реакции ~0.25 с (бот видит состояние с опозданием);
- разброс прицела (случайное отклонение угла);
- решение принимается раз в 3–4 кадра, не каждый кадр.

Без них бот играет нечеловечески хорошо, и выводы о сложности ложные.

**Сценарии:**
1. Режим `original`: сколько волн бот проживает (20 зёрен).
2. Кампания: каждый уровень отдельно (старт через `CFG.campaignStart`), 10–20 зёрен на уровень.
3. Миссия «Расейняй» (`story`): доля прохождений и место гибели.

**Метрики (сохраняются в отчёт):**
- доля прохождения каждого уровня или волны;
- причины гибели: тип врага, нанёсшего последний урон (игрока или базы);
- полученный урон по типам врагов;
- время прохождения уровня;
- подобранные и использованные бонусы.

**Примеры проверок:**
- Уровень 1 кампании бот проходит в ≥ 90% запусков.
- Доля прохождения не падает больше чем на 30 п.п. между соседними уровнями (нет скачков).
- Ни один тип врага не даёт больше 50% гибелей бота.

**Время прогона:** 1–10 мин на 12 ядрах. **Запуск вручную после правок баланса, не в каждом `check.cjs`.**

### Уровень 4. Эволюция параметров бота (десятки минут)

Генетический алгоритм подбирает параметры бота уровня 3 (6–10 чисел).

**Цикл:**
1. Популяция 50–100 наборов параметров.
2. Каждый набор играет 3 зерна. Зёрна **меняются каждое поколение**.
3. Оценка (fitness):
   ```
   fitness = 1000 × пройдено_уровней
           + 100  × пройдено_волн
           + 1    × уничтожено_врагов
           + 0.1  × секунд_выжито
           − штраф за разрушенную базу
   ```
4. 20% лучших остаются, остальные заменяются потомками: скрещивание двух родителей и мутация (шум к параметрам).
5. 30–100 поколений.

**Обучение по нарастающей:** сначала уровни 1–3, потом добавлять следующие. Слабые агенты останавливаются досрочно, как только станет ясно, что лучших им не догнать.

**Результаты:**
- Лучший набор параметров записывается в `scripts/balance/champion.json`, он становится «эталонным игроком» для уровня 3.
- Читаемые выводы о стратегии: «лучший бот держит дистанцию 280 и игнорирует бонусы» — повод пересмотреть бонусы.
- Уровень, на котором популяция застревает дольше всего, — кандидат на скачок сложности.

**Проверка на переобучение:** чемпион прогоняется на 20 отложенных зёрнах, которые не участвовали в эволюции. Результат должен быть не хуже чем на 15–20% от результата на обучающих зёрнах.

**Время прогона:** 15–60 мин. **Запуск вручную или ночью.**

### Уровень 5. Нейроэволюция (часы, по желанию)

Вместо параметров скриптового бота эволюционируют веса маленькой нейросети (подход типа NEAT или Evolution Strategies). Обратное распространение, датасет и GPU не нужны.

**Вход сети (~30–40 чисел):**
- свой танк: HP, улучшение, перезарядка, угол корпуса;
- 3–4 ближайших врага: направление и расстояние относительно своего танка, тип, HP;
- ближайший снаряд, летящий в игрока: направление, расстояние;
- 8 лучей до препятствий (стена, кирпич, вода);
- база: направление, расстояние, HP;
- ближайший бонус.

**Выход:** газ/назад, поворот корпуса, угол прицела, огонь, спецспособность.

Оценка, смена зёрен, ограничения «как у человека» и обучение по нарастающей — как на уровнях 3–4.

**Зачем, если есть уровень 4:** нейросеть не ограничена правилами, которые придумал человек, и находит неожиданные стратегии и эксплойты (застревание AI в углах, стрельба сквозь щели, подрыв врагов на своих минах). Найденные эксплойты оформляются как баги AI, а не как успех баланса.

**Оценка стоимости:** прогон кампании целиком «в лоб» — сутки и больше. С обучением по нарастающей и досрочной остановкой — несколько часов.

**Время прогона:** часы. **Только ночной эксперимент, результат — отчёт.**

## 5. Как формулировать цели

Шаблон:

> **В ситуации** S **метрика** M **должна быть** в диапазоне [a, b] **в** P% запусков.

| Замысел словами | Ситуация | Метрика | Коридор |
|---|---|---|---|
| «Тяжёлый танк — самый опасный» | Дуэль, игрок стоит | Время до гибели | heavy быстрее всех остальных |
| «Первая волна проходится почти всегда» | Бот, волна 1 | Выжил ли | ≥ 90% запусков |
| «Сложность растёт плавно» | Состав волн 1–15 | Суммарное HP | +10…+40% к прошлой волне |
| «Разведчик слабый, но надоедливый» | Активная дуэль | Победа / потеря HP | победа 85–100%, теряет ≥ 1 HP в 30% случаев |
| «Улучшение танка ощутимо» | Дуэль с soldier, upgrade 0 и 2 | Время победы | upgrade 2 хотя бы в 1.5 раза быстрее |
| «В кампании нет стены сложности» | Бот, уровни 1–15 | Доля прохождения | падение ≤ 30 п.п. между соседними |

**Порядок работы с целями:**
1. Тестер собирает текущие метрики (`--report`) и предлагает коридоры: текущее значение ±25%.
2. Автор игры утверждает или правит коридоры словами («heavy должен быть опаснее»).
3. Тестер переводит утверждённый замысел в проверки.
4. Каждая проверка в коде снабжается комментарием с замыслом словами.

**Ширина коридора:**
- слишком узкий (±5%) — тест падает от мелочей, ему перестают верить;
- слишком широкий — тест ничего не ловит;
- если автор хочет изменить баланс, **сначала сдвигается коридор** (новый замысел), потом подгоняется игра.

## 6. Правила для правок игры, чтобы тесты оставались рабочими

### 6.1. Безопасно
- **Числа в `js/config.js`** (`KINDS`, `CFG`, `MG_TIERS`, `ROCKET_CONFIG` и т. д.). Тест может упасть, и в этом его смысл.
- **Графика, звук, интерфейс, тексты**: `render-*.js`, `audio.js`, `ui-text.js`, CSS, картинки.
- **Новые карты, правки AI внутри функций**: метрики изменятся, контракт останется.
- **Новый тип врага или бонуса.** Ничего не сломается, но тест его не увидит, пока сценарий не добавят в уровни 1–2.

### 6.2. Потребуется правка `sim.cjs`
- Переименование `KINDS`, `CFG`, `waveList`, `maxAlive`, `makeTank`, `startGame`, `update`, `player`, `enemies`, `allies`, `toSpawn`, `grid`, `EMPTY`, `base`, `wave`, `state`, `campaign`, `keys`, `mouse`.
- Изменение аргументов `waveList(w)`, `makeTank(x, y, kind)`, `setPlayerUpgrade(t, n)`.
- Перенос общего состояния из глобальных переменных в замыкания или модули.
- Иные названия состояний игры (`state === 'over'`) или признака гибели (`player.dead`).

Такие поломки видны сразу (`... is not defined`) и чинятся в одном месте.

### 6.3. Ломает незаметно — запрещено в игровой логике
1. **Другой источник случайности** (`crypto.getRandomValues`, зерно из `Date.now()`). Пропадает детерминизм, тесты начинают «мигать». Вся случайность только через `Math.random` (или построенные на нём `rnd`/`ri`).
2. **Реальное время внутри `update`** (`performance.now()`, `Date.now()`). Логика знает время только через `dt`. Сейчас `performance.now()` есть только в игровом цикле (`index.html`), и это правильно.
3. **Таймеры** (`setTimeout`, `setInterval`) для игровых событий. В тестах это пустышка: событие никогда не случится. Таймеры делаются счётчиком, который уменьшается на `dt` внутри `update` (как сейчас).
4. **Логика, зависящая от загрузки картинок или от DOM**, например хитбокс по размеру спрайта. Все игровые размеры живут в конфиге.

Сейчас все четыре правила соблюдаются (проверено 08.11.2026). Желательно добавить в `check.cjs` проверку, что в `js/*.js` (кроме рендера, звука и редакторов) нет `setTimeout`, `setInterval`, `Date.now`, `performance.now`, `crypto`.

### 6.4. Особенность случайности
Любой новый вызов `Math.random()` (даже для разброса искр) сдвигает всю дальнейшую последовательность случайных чисел, и бой с конкретным зерном идёт иначе. Тесты с медианой по 20+ зёрнам и коридорами это переживают, тесты на точное значение — нет. Это ещё одна причина для правила 3.1.

Если визуальные эффекты начнут заметно влиять на последовательность, можно завести для них отдельный генератор, не связанный с игровой логикой.

## 7. Что делать, когда тест баланса упал

1. Запустить `--report` и посмотреть, какие метрики сдвинулись и насколько.
2. Определить причину: правка чисел, правка AI или побочный эффект другой правки.
3. Решить вместе с автором:
   - **ошибка** — откатить или исправить игру;
   - **задумано** — обновить коридор и/или `--save` снимок **в том же коммите**, указав причину в сообщении коммита.
4. Никогда не расширять коридор молча, лишь бы тест прошёл.

## 8. Файлы и команды

```
scripts/balance/
  boot.cjs           загрузка игры в песочницу с зерном
  sim.cjs            слой управления: reset / spawn / step / observe / act
  stats.cjs          медиана, перцентили, таблицы
  bot.cjs            скриптовый бот (уровень 3)
  evolve.cjs         эволюция параметров бота (уровень 4)
  neuro.cjs          нейроэволюция (уровень 5, по желанию)
  workers.cjs        распределение прогонов по ядрам (node:worker_threads)
  champion.json      лучшие параметры бота
check-balance.cjs    уровни 1–2, коридоры
balance-baseline.json  снимок метрик для --report
```

| Команда | Уровни | Время | Когда |
|---|---|---|---|
| `node check.cjs` | 1 + быстрая часть 2 | +несколько секунд | Перед каждым коммитом |
| `node check-balance.cjs [--report] [--save]` | 1–2 | < 30 с | После правки чисел |
| `node scripts/balance/bot.cjs [--report]` | 3 | 1–10 мин | После заметных правок баланса или AI |
| `node scripts/balance/evolve.cjs` | 4 | 15–60 мин | Вручную или ночью |
| `node scripts/balance/neuro.cjs` | 5 | часы | Ночной эксперимент |

Результаты уровней 3–5 сохраняются в `docs/balance-report-ГГГГ-ММ-ДД.md` (таблицы метрик, выводы, замеченные эксплойты).

## 9. Порядок работ и критерии приёмки

| # | Этап | Критерий приёмки |
|---|---|---|
| 1 | Уровень 0: `boot`, `sim`, `stats` | Детерминизм подтверждён. Существующие `check-*.cjs` не сломаны |
| 2 | Уровень 1 | Таблица волн 1–15 в `--report`. Проверки монотонности сложности. Включено в `check.cjs` |
| 3 | Уровень 2 | Дуэли для всех типов врагов, `--report` + `--save`, сравнение со снимком в процентах |
| 4 | Согласование коридоров с автором | Каждая проверка имеет утверждённый замысел в комментарии |
| 5 | Уровень 3 | Бот с ограничениями «как у человека». Отчёт по уровням кампании и причинам гибели |
| 6 | Уровень 4 | `champion.json`. Проверка на отложенных зёрнах. Отчёт со стратегией чемпиона |
| 7 | Уровень 5 (по желанию) | Ночной прогон, отчёт со стратегиями и найденными эксплойтами |
| 8 | Защита контракта | Проверка в `check.cjs` на запрещённые таймеры, время и случайность в логике |
